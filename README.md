# Hotel Reservation Service

REST API бронирования отелей: Java 21, Spring Boot 3.5, PostgreSQL 16, Kafka, MongoDB 7, Flyway, MapStruct.

## Постоянный локальный сайт

Для frontend + настоящего backend используйте отдельное окружение. Нужны Docker Desktop, Java 21 и Node.js 22+; один раз установите зависимости через `cd frontend && npm ci`.

Из корня репозитория:

```bash
./dev start
```

На macOS скрипт обнаруживает установленный JDK 21; при необходимости укажите JAVA_HOME. Откройте http://127.0.0.1:3000/. Логин — `local-user`, случайный пароль находится в закрытом файле `.local/login.txt`. Пароли БД и ключ quote хранятся в `.local/credentials.json`, не выводятся в консоль и исключены из Git. Не публикуйте эти файлы и не удаляйте `.local/`: для уже существующих томов скрипт откажется генерировать новые пароли вместо утраченных.

```bash
./dev status
./dev stop
```

Ctrl+C тоже останавливает приложение и контейнеры, **сохраняя все данные**. Следующий `./dev start` возвращает тот же каталог, пользователей, сессии и брони. Приложение работает из копии JAR в `.local/`, а не внутри Maven-теста; ограничения preview на три часа нет. Старт выполняет сборку JAR без тестов; проверки выполняются отдельно командами ниже. Во время стартовой Maven-сборки не запускайте другой Maven; перед frontend build остановите Next этим же `./dev stop`.

Из `frontend/` доступны эквивалентные `npm run local:start`, `local:stop`, `local:status`. Старый `npm run dev:isolated` остаётся временной тестовой средой с отдельными данными. Два режима одновременно не запускаются: оба занимают порт 3000.

Инфраструктура описана отдельно в `compose.local.yml`, Compose project `hotel-local-app`, тома PostgreSQL/MongoDB/Kafka имеют собственные имена. Порты только loopback: frontend 3000, backend 18080, PostgreSQL 15433, MongoDB 17017, Kafka 19092. Исходный docker-compose.yml, существующая `.env` и прежние рабочие базы не используются. На первом запуске Flyway создаёт новую схему; baseline выключен и Hibernate остаётся validate. Локальный профиль проверяет назначение БД **до Flyway**. Профиль не предназначен для ручного перенаправления на старую БД.

Первое заполнение создаёт обычного USER и 3 вымышленных отеля/6 комнат (Москва, Санкт-Петербург, Казань). Повторный запуск не меняет цены/описания/пароль и не возвращает удалённые объекты. Завершённую инициализацию фиксирует отдельный маркер в БД. Фото для оформления не выдаются за реальные фото этих объектов.

### Управление отелями

Откройте http://127.0.0.1:3000/admin. Отдельный локальный администратор — `local-admin`, пароль находится в закрытом файле `.local/admin-login.txt`. Если уже выполнен вход как `local-user`, сначала выйдите из аккаунта. При обновлении существующего локального окружения launcher сохраняет прежние credentials, добавляет административные и делает закрытую резервную копию. Обычный пользователь не получает роль ADMIN. Повторный старт не меняет пароли существующих пользователей.

Администратор может создавать и редактировать отели/номера, задавать цены, загружать JPEG/PNG до 5 МБ, публиковать и скрывать объекты. Сначала сохраните отель, затем добавьте номера. Для фотографии укажите описание, автора и лицензию. Загруженные файлы сохраняются в `.local/media/`; backup должен включать и эту папку. Снятие с публикации сохраняет историю бронирований. При конфликте версий форма просит перечитать данные. Безвозвратное удаление через эту админку не предусмотрено. Все созданные объекты пока относятся к вымышленному локальному демокаталогу.

Изображения проверяются по содержимому и повторно кодируются; произвольные URL, SVG, пути файловой системы и слишком большие изображения отклоняются. API защищён JDBC-сессией, ролью ADMIN, CSRF и Origin. Для production нужна отдельная конфигурация хранилища и резервного копирования.

Постоянные тома не заменяют резервную копию. Перед переносом проекта/переустановкой Docker сохраните согласованные резервные копии БД и `.local/credentials.json`; автоматический backup/restore будет отдельной проверяемой задачей. Команды удаления томов в launcher отсутствуют.

## Запуск существующего backend с прежней инфраструктурой


Нужны JDK 21 и работающий Docker с Compose. Приложение запускается на хосте, инфраструктура — в контейнерах.

1. Скопируйте `.env.example` в `.env`. Замените оба пароля разными случайными значениями. `.env` исключён из Git. Если пароль MongoDB содержит специальные символы URI, задайте их percent-encoded представление в URI или используйте пароль из URI-safe символов.
2. Для **существующей базы** сначала выполните раздел миграции ниже. Не удаляйте Docker volumes для обхода ошибок.
3. Запустите инфраструктуру:

```bash
docker compose up -d --wait
```

4. Запустите приложение:

```bash
./mvnw spring-boot:run
```

Flyway создаёт схему чистой БД, Hibernate только проверяет её (`ddl-auto=validate`). Пароли по умолчанию отсутствуют. PostgreSQL доступен на `127.0.0.1:5433`, MongoDB — `127.0.0.1:27017`, Kafka — `localhost:9092`. Для другого приложения внутри Compose используйте `kafka:29092`. Это конфигурация локальной разработки; для внешнего доступа нужны HTTPS и защищённые подключения к инфраструктуре.

## Первый администратор

Регистрация `/api/v1/auth/register` всегда создаёт USER. Для первоначального ADMIN временно заполните в `.env`:

```properties
BOOTSTRAP_ADMIN_ENABLED=true
BOOTSTRAP_ADMIN_NAME=admin
BOOTSTRAP_ADMIN_EMAIL=your-real-admin-address@example.com
BOOTSTRAP_ADMIN_PASSWORD=replace-with-a-unique-random-password
```

Пароль: не менее 12 символов, не более 72 UTF-8 байт. После успешного первого запуска установите `BOOTSTRAP_ADMIN_ENABLED=false`, удалите `BOOTSTRAP_ADMIN_PASSWORD` и перезапустите приложение. Существующий аккаунт автоматически не повышается в правах; пароль существующего ADMIN не сбрасывается. Конфликт имени/email останавливает bootstrap с понятной ошибкой.

Swagger: `http://localhost:8080/swagger-ui/index.html`, OpenAPI: `http://localhost:8080/v3/api-docs`. Оба требуют ADMIN через HTTP Basic.

| Операция | USER | ADMIN |
|---|---|---|
| Регистрация | Доступна без входа; только роль USER | То же |
| Чтение отелей и комнат, поиск | Да | Да |
| Создание/изменение/удаление отелей и комнат | Нет | Да |
| Оценка отеля | Да | Да |
| Создание бронирования | От собственного имени | От собственного имени |
| Список и чтение бронирований | Только свои | Все |
| Чтение/изменение профиля | Только свой | Любой |
| Список/поиск/создание/удаление пользователей, смена роли | Нет | Да |
| CSV статистики | Нет | Да |

Для REST-клиентов: HTTP Basic, JSON `Content-Type: application/json`. Пример регистрации:

```bash
curl -i http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"name":"alice","email":"alice@example.com","password":"replace-this-password"}'
```

Браузерные изменяющие запросы защищены CSRF. Сначала выполните `GET /api/v1/auth/csrf`, сохраните cookie и передайте возвращённый JSON `token` в заголовке с именем `headerName`, сохраняя ту же cookie. JSON token — представление для отправки в заголовке; не заменяйте его содержимым cookie. Запросы с `Origin`, `Referer` или `Sec-Fetch-Site` требуют токен. Swagger при изменяющих запросах также должен передавать токен. CORS для сторонних origins не разрешён.

## Бронирования и поиск

Создание: `POST /api/v1/bookings` с `roomId`, `checkInDate`, `checkOutDate`. Даты — ISO `YYYY-MM-DD`, заезд в будущем, выезд позже заезда. Владельца определяет аутентификация. Старое поле `userId` допускается только если совпадает с текущим пользователем; чужой ID даёт 403.

Интервалы полуоткрытые: `[заезд, выезд)`. Заезд в день чужого выезда разрешён. Строка комнаты блокируется до проверки и сохранения брони; конфликт возвращает 409. Список бронирований USER автоматически ограничен владельцем.

`GET /api/v1/rooms/filter`: положительные числовые `id`, `hotelId`, `capacity`; точные десятичные `priceMin`/`priceMax`; `name`; необязательная **пара** `checkInDate`/`checkOutDate`. Одна дата, обратный порядок или min > max дают 400. Цена комнаты хранится как numeric(38,2); лишние знаки после запятой отклоняются.

`GET /api/v1/hotels/filter`: `id`, `name`, `title`, `city`, `address`, диапазоны расстояния, рейтинга и количества оценок. Диапазоны проверяются. Пагинация: `page >= 0`, `size` от 1 до 100.

`unavailableDates` во всех ответах комнат (включая вложенные `roomsList`) — отсортированные занятые дни только в окне `availabilityFrom` включительно — `availabilityUntil` исключительно: UTC-сегодня и следующие 365 дней. Выезд не включается. Поиск доступности и история бронирований этим окном не ограничиваются.

`PATCH /api/v1/hotels/{id}/rating?rating=...`: конечное число 1..5, максимум четыре ненулевых знака после запятой. Среднее рассчитывается из точной суммы и количества, округляется до одного знака для ответа. Конкурирующие обновления защищены версией; при 409 клиент может повторить запрос.

Удаление комнаты/отеля с любой историей бронирований запрещено (409). Удаление пользователя с бронями также блокируется внешним ключом. Удаление отеля без бронирований удаляет его комнаты без бронирований.

## Kafka, outbox и статистика

Регистрация и бронирование сохраняют событие в `outbox_events` в той же транзакции PostgreSQL. Недоступность Kafka не отменяет успешную бизнес-операцию. Планировщик выбирает ограниченную пачку с `FOR UPDATE SKIP LOCKED`, публикует её и отмечает отправку только после Kafka ack. Ошибки повторяются с увеличением задержки; после сбоя фиксации БД возможен повтор уже отправленного события.

Ключ Kafka — UUID outbox-события. Consumer использует его как MongoDB `_id`, поэтому повторная доставка не создаёт второй документ. Гарантия доставки — at least once. После ограниченных попыток ошибочные сообщения попадают в `user-events.DLT` / `booking-events.DLT`; неуспешная отправка в DLT не подтверждает исходное сообщение. Некорректные JSON-байты сохраняются в DLT без перекодирования. Старые Kafka-сообщения без ключа направляются в DLT для ручного разбора.

Оба исходных топика и DLT создаются KafkaAdmin. Для локального брокера replicas=1. При увеличении партиций исходных топиков увеличьте их и у DLT. Настройки с текущими значениями по умолчанию:

```yaml
app:
  outbox:
    enabled: true
    poll-interval-ms: 1000
    batch-size: 20
    ack-timeout-seconds: 10
  kafka:
    topic-partitions: 3
    topic-replicas: 1
```

Отправленные outbox-строки сохраняются; для длительной эксплуатации нужна отдельная политика архивирования. При недоступном брокере блокировки удерживаются на время ограниченных попыток отправки, поэтому не увеличивайте размер пачки без проверки нагрузки.

`GET /api/v1/admin/statistics/export` отдаёт UTF-8 CSV потоково, ограниченными страницами. Числовые ID и даты форматируются безопасно, CSV-кавычки и переносы экранируются. Старые MongoDB `_id` типов ObjectId/число и новые UUID-строки экспортируются вместе без изменения исходных документов. Экспорт отражает живые данные, а не транзакционный снимок одновременно поступающих событий.

## Миграция существующей PostgreSQL БД

Приложение не выполняет baseline автоматически. Сначала сделайте резервную копию и проверьте схему/данные. Изменения не удаляют таблицы или историю.

Для исходной схемы проекта без `flyway_schema_history`:

1. Проверьте соответствие таблиц миграции `V1__initial_schema.sql` и отсутствие дублей:

```sql
SELECT name, count(*) FROM hotels GROUP BY name HAVING count(*) > 1;
SELECT id FROM bookings WHERE check_in_date >= check_out_date;
SELECT id FROM rooms WHERE number <= 0 OR price <= 0 OR room_capacity <= 0;
SELECT id FROM hotels WHERE distance_from_city_center < 0 OR count_of_ratings < 0;
```

2. Дубли названий отелей нужно разрешить вручную: V4 добавляет уникальный индекс и откажется его создавать при дублях. Исторические ошибки значений не исправляются автоматически: CHECK из V4 с `NOT VALID` сохраняет старые строки, но защищает новые/обновляемые. После исправления истории администратор БД может явно выполнить `VALIDATE CONSTRAINT`.
3. Только для проверенной исходной схемы однократно запустите:

```bash
SPRING_FLYWAY_BASELINE_ON_MIGRATE=true SPRING_FLYWAY_BASELINE_VERSION=0 ./mvnw spring-boot:run
```

Baseline именно **0**, чтобы применились V1, V2, V3 и V4. При уже существующей истории Flyway не создавайте новый baseline: сначала проверьте её. После перехода запускайте обычной командой без этих переменных.

V2 восстанавливает доступную сумму рейтинга из старого среднего и количества; точные исторические оценки из округлённого среднего восстановить невозможно. Новые оценки считаются без такого накопления погрешности.

## Тесты и CI

```bash
./mvnw test
./mvnw -Pintegration verify
```

Первая команда запускает модульные и HTTP-тесты без внешних сервисов. Вторая включает интеграционные тесты на изолированных Testcontainers PostgreSQL, Kafka и MongoDB. Они не используют рабочую БД. При недоступном Docker интеграционные тесты помечаются как пропущенные — такой запуск не доказывает работоспособность инфраструктуры.

GitHub Actions запускает оба набора на Java 21; отдельный `docker info` не позволяет CI молча пропустить инфраструктурную проверку из-за отсутствия Docker. Отчёты сохраняются как artifact `test-reports`. Mockito подключается как javaagent, без ненадёжного динамического self-attach.

## Browser API v2: основной сценарий сайта

Новая реализация находится в `web/v2/`: `auth` отвечает за браузерный вход, `catalog` — за публичное чтение, `booking` — за расчёт/создание/отмену, `common` — за валидацию HTTP и ошибки. Существующий `/api/v1` остаётся отдельным legacy Basic API; серверная v2-сессия его не авторизует. Полный целевой контракт и ограничения релиза описаны в `../docs/API_CONTRACT.md`.

V2 включается **явно**, после проверки миграций и перехода старых клиентов:

```properties
BROWSER_API_ENABLED=true
BROWSER_QUOTE_ENCRYPTION_KEY=<base64-encoded-32-random-bytes>
```

Ключ создаётся отдельно для окружения, например `openssl rand -base64 32`, и хранится в секретах окружения, вне Git и логов. Не используйте тестовый ключ. Ключ нужен для зашифрованных записей восстановления расчёта; сохраняйте его отдельно вместе с защищённым планом восстановления. Ротация с поддержкой нескольких ключей пока не реализована. Пустой/неверный ключ при включённом v2 останавливает запуск. При выключенном флаге v2 закрыт; флаг не пропускает новые миграции.

При включении v2 старые POST `/api/v1/auth/register` и `/api/v1/bookings` возвращают **410**: старый запрос не содержит гостей и согласия с ценой. Browser/cookie unsafe-запросы v1 запрещены; legacy Basic read/admin доступ в публичном размещении должен быть ограничен ingress/network policy. Не включайте v2 до согласованного перехода старых write-клиентов.

### Доступ и сессия

V2 требует HTTPS в реальном окружении. Cookie `__Host-hotel-session` имеет Secure/HttpOnly/SameSite=Lax; через обычный HTTP браузер такой вход не обслуживает. TLS/reverse proxy, доверенные forwarding headers и изоляция backend будут частью deployment-пакета. Локальный preview использует отдельный development HTTP-режим в Next-адаптере: он переводит cookie в `hotel-local-session` без Secure и обратно; настройки backend остаются прежними. Модульные HTTP-тесты и Testcontainers проверяют HTTPS-сценарий через тестовый HTTP-слой; приложение к рабочей БД в этой задаче не запускалось.

Последовательность браузера: GET `/api/v2/auth/csrf` → POST `/auth/login` с `username/password`, cookie и `X-CSRF-TOKEN` → GET новый csrf → GET `/auth/me`. CSRF обязателен для всех изменений, включая вход/выход. Cookie хранит только идентификатор; сессия лежит в PostgreSQL (Spring Session JDBC), переживает перезапуск/доступна экземплярам приложения. Idle timeout 30 минут, абсолютный 12 часов; при изменении роли/имени/email/пароля версия безопасности в БД отзывает старые сессии. Лимиты попыток хранятся в БД; сырые пароли и источники туда не пишутся.

Публичная регистрация закрыта до отдельной реализации email-подтверждения/восстановления. TEST_ONLY включается только активным test-профилем, серверными параметрами и loopback-доступом; это не публичная деморегистрация и не общий администратор.

### Каталог

Публичные GET: `/api/v2/cities`, `/hotels`, `/hotels/{slug}`, `/hotels/{slug}/rooms`, `/rooms/{roomId}`. Не возвращают владельцев, брони или занятые даты чужих гостей. Поиск с датами включает только отели с подходящей свободной комнатой; цена «от» взята по тому же набору комнат. Без дат цена за ночь не обещает доступность. Город задаётся кодом из `/cities`, цены — decimal strings, даты — парой `YYYY-MM-DD`, гости — целым числом.

V6 оставляет старые объекты **неопубликованными** и не подставляет им slug/TZ/координаты. Каталог может быть пустым, пока администратор явно не настроит достоверные метаданные. В локальном v2 доступны административный интерфейс, загрузка JPEG/PNG и публичная выдача `/media/...`; V8 добавляет optimistic version номера и маркер начального наполнения. Legacy-база автоматически не заполняется и не очищается. Наполнение доступно только в отдельном защищённом local-профиле. Публичный первый релиз ограничен явно вымышленными объектами (`demo=true`).

### Бронирование

POST `/api/v2/bookings/quote` принимает roomId (строка), checkInDate/checkOutDate, guests и UUIDv4 `Idempotency-Key`. Quote действует 10 минут, хранится для replay 24 часа и **не держит комнату**. После проверки пользователь явно подтверждает POST `/bookings` с тем же выбором и `quoteToken`, используя новый CREATE key.

Цена считается сервером: фиксированный тариф за комнату × календарные ночи, RUB, без оплаты/доплат. Заезд от завтра в TZ отеля, 1–30 ночей, выезд в пределах 365 дней. Room lock сериализует создание, отмену и изменения тарифа; PostgreSQL exclusion constraint дополнительно запрещает пересечение CONFIRMED интервалов. Цена/гости/названия/TZ/deadline сохраняются в брони; каталог не переписывает подтверждение.

При изменении цены/условий — 409 и новый расчёт без создания, после чего нужно отдельное согласие и новый CREATE key. Потеря связи после POST означает неизвестный исход: GET `/me/booking-operations/result` с прежним ключом в заголовке. Успешный POST можно повторить с этим ключом **без тела и истёкшего quote**, он вернёт ту же квитанцию. 404 операции сам по себе не доказывает отсутствие запоздавшего запроса. POST `/me/booking-operations/fence` с тем же ключом закрывает ещё непринятый запрос либо возвращает известное состояние; он не отменяет созданную/выполняющуюся бронь. Полная схема recovery описана в контракте.

Свои записи: GET `/me/bookings`, GET `/me/bookings/{id}`; отдельный ADMIN read scope `/admin/bookings`. ADMIN `/me` также показывает только свои записи. POST `/me/bookings/{id}/cancel` меняет CONFIRMED → CANCELLED до сохранённого начала дня заезда, сохраняя историю и освобождая даты. Повтор отмены безопасен. Событие отмены сохраняется вместе со статусом в outbox и поступает в Kafka/Mongo как BOOKING_CANCELLED; CSV сохраняет прежние колонки. Объекты с историей не удаляются.

### Дополнительная проверка миграций

V5 создаёт JDBC session/rate/security-version таблицы и trigger отзыва сессий, V6 — metadata/photos, V7 — снимки брони и durable quote/operation registry. Для V7 требуется установленное расширение PostgreSQL `btree_gist` (либо право установить его). На существующей БД перед миграцией найдите пересекающиеся действующие старые брони:

```sql
SELECT a.id, b.id, a.room_id
FROM bookings a JOIN bookings b ON a.room_id=b.room_id AND a.id<b.id
WHERE a.check_in_date<a.check_out_date AND b.check_in_date<b.check_out_date
  AND a.check_in_date<b.check_out_date AND a.check_out_date>b.check_in_date;
```

До V7 все старые записи считаются CONFIRMED. При существующих пересечениях migration остановится: нужен явный разбор, а не удаление volumes/истории или отключение ограничения. Сделайте backup и проверяйте переход на копии. Существующий Flyway history продолжается, новый baseline не выполняется.

Старые записи получают origin LEGACY, а цена/гости/время создания/snapshot остаются неизвестными. UI должен показать «Стоимость не сохранена». Без проверенного per-record TZ и audit provenance MIGRATION_VERIFIED старая бронь не получает self-cancel: сервер не угадывает её часовой пояс по браузеру или городу. Политика ручной проверки описана в контракте; операторский endpoint пока не добавлен.

Успешные CREATE receipts/key bindings и terminal tombstones сохраняются с историей без TTL; full error recovery очищается через 7 суток, quote records — через 24 часа. Ограничение бюджета записей и мониторинг размера обязательны для последующего публичного размещения. Тесты используют только временные контейнеры, не рабочие volumes.

## Frontend

В `frontend/` находится Next.js/TypeScript приложение: главная, каталог/отель, вход, расчёт и подтверждение брони, восстановление результата, свои брони/детали/отмена. Это отдельный процесс, использующий browser API v2. Запуск, локальный HTTP-режим, граница адаптера и проверки описаны в [frontend/README.md](frontend/README.md). Реальный HTTPS-протокол проверен в изолированном окружении; полная браузерная приёмка и публичное размещение остаются отдельными этапами.

`npm run dev:isolated` из frontend запускает временные Testcontainers и настоящий Spring через opt-in manual test, затем локальный HTTP frontend на http://127.0.0.1:3000. Не запускайте другой Maven-процесс, пока работает этот preview; обычный integration suite исключает manual-тест. Рабочая БД и volumes в этой проверке не используются.


## Непрерывные проверки

GitHub Actions workflow `.github/workflows/verify.yml` запускает на push и pull_request две независимые задачи: Java21 unit/HTTP + PostgreSQL/Kafka/MongoDB integration tests и frontend на Node.js26. Frontend устанавливается через `npm ci`, проверяет контракт `docs/api/`, генерирует и сравнивает типы API, выполняет тесты, production build и TypeScript. Сохранённые типы должны соответствовать OpenAPI. Frontend-задаче не нужны Docker, БД или секреты. Это CI, без deployment; публикация workflow в GitHub ещё требует отправки локальных изменений.

Контракт и его fixtures теперь хранятся внутри репозитория: `docs/API_CONTRACT.md`, `docs/api/`. Внешние проектные документы не требуются для сборки после clone. Локальные команды и ограничения параллельной работы Next — в [frontend/README.md](frontend/README.md).
